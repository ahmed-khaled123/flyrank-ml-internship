Refresh Signal: ranking which pages are about to lose search demand

A client-grouped model for prioritizing a content refresh queue, benchmarked honestly against a position-based heuristic and the no-skill floor — including a label-leakage bug I caught in my own pipeline before trusting the results.

Lane 2 — Refresh / Content Opportunity Scoring · Warehouse partition: March 2026 · Ahmed Khaled
Abstract

Content teams learn a page is losing search visibility only once it shows up in a monthly report — by then the drop has already happened. This project frames early detection as a ranking problem: score every page a client publishes by how likely it is to see a meaningful drop in organic search demand over the next two weeks, using only signal available before that window starts. A random-forest model trained on prior-window search metrics is evaluated with a client-grouped train/test split (so no client's editorial style is seen in both train and test) against a CTR-gap heuristic baseline and the honest no-skill floor. On 8 held-out clients the model reaches Precision@20 of 0.75 and Precision@50 of 0.78, against 0.35 / 0.46 for the baseline and 0.51 for a random ranking. An earlier version of the label definition produced a suspiciously perfect result (ROC-AUC ≈ 0.97) that turned out to be a self-inflicted leakage bug, caught and fixed before these numbers were reported — that process is documented alongside the results, because catching it mattered as much as the score itself.

01

Introduction & problem

A content team managing hundreds of client pages cannot manually watch every page's search performance every day. In practice, decline is noticed retroactively — a monthly report shows impressions or clicks down for a page, and by then the page has already been losing visibility for weeks. The team's real question is not "did this page decline," it's "which of my pages, right now, are about to?" — early enough that an editor can refresh the title, snippet, or content before the drop compounds.

This is the decision the model below is built to support: which pages to put at the top of a weekly refresh review queue. A page flagged and reviewed that turns out to be fine costs an editor a few minutes. A real decliner that isn't flagged simply doesn't reach the top of this week's queue — a delayed cost, not a silent one — which is why this is framed as a ranking problem (a prioritized list judged by Precision@K) rather than a binary classifier a team is expected to obey.

02

Data

The analysis uses one monthly warehouse partition — fact_content_daily_performance, month=2026-03 — joined to a content dimension table for page metadata. The month is split in half in time, not by a random row sample, so the setup genuinely predicts forward rather than interpolating within one window:

Mar 16–31target window · label computed here

Only rows with confirmed Google Search Console coverage are used — roughly 37% of the raw partition, per the data contract established earlier in this internship. The remaining rows have no impression, click, or position data to build a trend from, so they are excluded rather than imputed. Pages with fewer than 10 prior-window impressions are also dropped: a page with 2 impressions going to 0 is noise, not a decline. After these filters, the working dataset covers 39 clients and roughly 114,700 pages.

03

Methodology

Label — is_declining. A page is labeled 1 if its daily impression rate in the target window is at least 20% lower than its daily impression rate in the prior window, else 0. Rates, not raw counts, because the two windows are different lengths (15 vs. 16 days). This is a current-window proxy for losing demand — a page could recover the following month, so the label describes a pattern in this data, not a certified permanent decline.

Features — all computed only from the prior window, so nothing here can see into the future it's trying to predict: prior impressions, prior clicks, prior CTR, prior average position, number of days with any impressions in the prior window, content age in days, and content type.

Baseline — a CTR-gap heuristic, not a fitted model: pages are bucketed by average position, an "expected CTR" is the training-set average CTR for that bucket, and the baseline score is max(0, expected_ctr − actual_ctr) × impressions. It asks how much click volume a page is leaving on the table for where it ranks — a reasonable heuristic, not a forecast.

Model — a random forest (300 trees, max depth 8, balanced class weights) trained on the six prior-window features to predict is_declining.

Validation — client-grouped, not random. The train/test split is an 80/20 split grouped by client_hash_id, so every page belonging to a client lands entirely on one side. A client's pages share editorial style and publishing cadence; a random row split would let the model partly memorize "how this client's pages behave" instead of learning something that generalizes to a client it has never seen. The gap this catches is shown directly in the results below.

A leakage bug I caught before trusting the result The first version of this label used clicks instead of impressions, with a strict "less than" comparison. Pages with zero prior clicks can never see target-window clicks go negative — so those pages were mechanically guaranteed a "not declining" label, regardless of anything else. That created a spurious, deterministic link between clicks_prior and the label. The tell was the pairing of results: the model scored an implausible ROC-AUC near 0.97 while a simple heuristic scored worse than random (0.14) on the same split — a "too good" model next to a "too bad" baseline is a leakage signature, not a win. Switching to an impressions-based rate with a genuine 20%-drop threshold removed the artifact; every number in Section 4 is from the corrected label.

Results vs. baseline

All numbers below are computed on the held-out test clients — 8 clients and 7,685 pages the model never saw during training.

Why report a "no-skill floor" instead of a random-permutation baseline: scoring a dummy/random classifier and ranking by its output produces a noisy, sometimes misleading number, since many implementations return tied scores that just reflect row order. The test-set base rate — what any ranking scores on average with zero skill — is the more honest and reproducible reference point, so it's reported directly instead.

The memorization-gap check. The same model, trained and evaluated with a random row-level split instead of the client-grouped one, reports ROC-AUC 0.684 — notably higher than the honest grouped-split score of 0.587. That gap is exactly the risk a random split hides: some of the apparent 0.684 is the model recognizing a client's own pages rather than learning a pattern that transfers to a client it has never seen. The number this paper stands behind is the grouped 0.587, not the more flattering 0.684.

Reading these numbers Directional claim (observed → directional, not causal, per the internship's own claim ladder): pages this model ranks highest are, on average, more likely to see a meaningful demand drop in the next two weeks than pages picked by the position-based heuristic, or by no ranking at all — a statement about relative ranking quality on this sample, not a guarantee for any individual page.

05

Limitations

  • One month, one partition. Every number above comes from March 2026 only. Nothing here has been checked against a different month or season, and a window spanning a holiday, algorithm update, or reporting anomaly could rank differently.
  • 8 held-out clients. The client-grouped split is strong on honesty — no client appears in both train and test — but 8 clients is a small population to claim the model generalizes to any new client; one unusual client can move these numbers.
  • GSC-only, ~37% of rows. Roughly 63% of the raw partition was excluded up front for missing search-console coverage. The model has nothing to say about those pages — the queue is silent on them, not confident they're fine.
  • The label is a proxy, not a certified outcome. A 20%-lower daily impression rate over 16 days is a reasonable stand-in for "losing demand," but a page could dip and recover, or be flagged off a small denominator.
  • A ranking aid, not an automated action. Precision in the 0.75–0.78 range means roughly one in four flagged pages is a false positive even at the model's best settings — workable for a reviewed queue, not for an unattended trigger.
  • Recommendation concentration. A naive "top pages by raw model score" pull concentrates heavily on a small number of clients and very low-traffic pages — a real pattern in how the score distributes, addressed directly in Section 6 rather than presented at face value.

Reading a row: the model score is a relative rank within this test set, not a probability to quote to a client. A production version of this queue would attach a reason code (model_decline_risk_high_confidence) and a suggested action (editorial_review_refresh_candidate) to each row for an editor, mirroring the action-scoring pattern used earlier in this internship's baseline work.

Where the model is confidently wrong — worth a reviewer's attention rather than blind trust. Three pages the model rated highest-risk (scores 0.69–0.70) were actually stable or growing; three pages it rated lowest-risk (scores 0.09–0.11) actually declined. Both error groups share a pattern: zero or near-zero prior CTR combined with mid-range position — exactly where the model's two heaviest features (content age and prior CTR) can point in conflicting directions.
